# 起源与设计演进

[English](origin-and-design-evolution.md) | 简体中文

Coordination Loop 并不是从“更多智能体组成更大的 swarm 就一定是更好的开发系统”这一假设出发。它的设计方向来自另一组逐步出现的压力：当个人的智能体辅助开发规模扩大时，执行身份越来越短暂，而项目身份必须保持稳定。

本文记录这种设计逻辑，但不会把私有开发历史当成公开产品状态。

## 阶段 1——一个人和一个智能体

最简单的模型很好用：开发者有一个仓库，打开一个编码智能体会话，请它完成一次修改，然后人工审阅并提交结果。

在这个环境里，活动对话很容易让人感觉几乎等同于活动开发上下文，因此“会话状态”和“项目状态”的区别很容易被忽略。

## 阶段 2——多个会话

当多个会话同时处理不同问题时，对话身份开始变得脆弱。开发者需要知道哪个会话拥有哪项修改、哪些假设仍然有效，以及其他会话是否已经改变了相关仓库状态。

第一个关键分离由此出现：

**会话身份不是开发身份。**

## 阶段 3——多个仓库与工作区

真实项目经常跨越不止一个仓库，而个人开发者也可能并行维护互不相关的项目。Git worktree、分支、CI 和集成边界都开始成为协调问题的一部分。

持久开发单元不能再等同于“当前终端里正打开的东西”。

## 阶段 4——多台机器

当工作在工作站、笔记本、服务器和云端 runner 之间移动时，机器本地状态已经不足以描述开发程序。某个进程可以消失，但它已经产生的仓库修改或外部副作用仍然可能存在。

因此第二个分离变得必要：

**机器身份不是开发身份。**

## 阶段 5——多个提供商与内部智能体图

不同提供商可能暴露完全不同的生命周期模型、子智能体系统、能力和证据。如果项目模型绑定其中任何一家，更换提供商就会变成一次架构迁移。

因此：

**提供商和智能体拓扑应该位于持久开发控制边界之下。**

## 阶段 6——权威开发连续性

最终得到的设计目标不是构建更大的智能体图，而是维护一个持久开发程序：其目标、权限、仓库/资源身份、证据和已接受状态能够跨越执行基底的变化继续存在。

这就导向门户当前公开的三条核心哲学：

- Goal 不是 Agent。
- 开发身份不是 Machine / Session / Provider。
- 声称完成不是权威状态迁移。

Coordination Loop 的四个产品是这套哲学不断演化的实现。哲学约束方向，而最终协议细节应该由实现证据决定。
