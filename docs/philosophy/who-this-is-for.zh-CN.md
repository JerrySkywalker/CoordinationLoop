# Coordination Loop 面向谁

[English](who-this-is-for.md) | 简体中文

Coordination Loop 首先面向个人开发者和小型工程团队：当编码智能体的使用规模已经超出单一对话、终端、仓库或机器时，需要一个更持久的开发控制层。

它并不首先把自己定位成企业级“AI 编排平台”。最初的压力来自一个更普通的问题：当自主执行加入日常软件开发后，个人和小团队的开发活动本身迅速变得难以持续管理。

## 同时推进多项工作的个人开发者

一个开发者可能同时维护多个项目、保留多个活动工作树、运行多个编码智能体会话，并让长时间任务在自己转移注意力后继续执行。

这时真正困难的是：哪个会话对应哪个目标，哪个仓库状态已经被准入，哪些工作可能仍在运行，以及现在究竟安全地允许做什么。Coordination Loop 希望让这些事实持久化，而不是每次从人的记忆和聊天记录中重新推断。

## 在多台机器之间工作的开发者

台式机、笔记本、工作站、家庭服务器和云端 runner 都可以成为有价值的执行位置，但它们不应该成为开发程序本身的身份。

当工作需要在机器之间迁移，同时保留精确仓库身份、权限、证据，以及对外部副作用不确定性的处理时，Coordination Loop 会更有价值。

## 预期未来会更换提供商的开发者

今天最合适的编码智能体未必是明天最合适的。一个项目可能从一个提供商迁移到另一个提供商，也可能针对不同能力使用不同提供商。

提供商独立意味着：持久开发模型应该表达所需能力和边界，而不是让某一家厂商的会话模型成为项目定义本身。

## 需要明确所有权的小团队

即使没有大型编排平台，小团队也可以从同一组原则获益：每个已准入资源只有受控写入者，高影响动作需要明确 owner 决策，交接可持久保存，委托有边界，并且证据可以独立于智能体叙述进行检查。

目标不是增加官僚流程，而是让越来越自主的开发工作仍然可理解、可追踪并可回退。

## 什么时候可能不需要 Coordination Loop

如果项目很短、只有一个仓库、全部工作都在一个交互会话中完成，而且几乎不需要持久委托和故障恢复，那么普通的 Git、CI、Issue 和编码智能体可能已经足够。

当开发开始跨越时间、仓库、机器、提供商、自主执行或共享权限时，Coordination Loop 的价值才会明显增加。
