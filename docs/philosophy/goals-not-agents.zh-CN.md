# 以目标为中心，而不是以智能体为中心

[English](goals-not-agents.md) | 简体中文

开发 Goal 是持久的逻辑进展单元；Agent 是可替换的执行机制。Coordination Loop 有意把这两种身份分开。

本文描述的是产品原则，而不是已经冻结的 Goal schema。

## 为什么这个区别重要

以智能体为中心的系统通常先问：下一个运行哪个智能体、智能体如何委托、planner 如何把工作拆成任务图。这些都是有价值的执行问题，但它们不足以定义一个软件项目的持久状态。

提供商可以重启智能体、替换模型、把工作扇出给多个子智能体，或者重组内部任务图。如果这些变化会重新定义项目的 Goal 身份，那么提供商内部的执行结构就意外地变成了项目事实源。

Coordination Loop 拒绝这种耦合。

## Goal 能跨越执行机制的替换

从产品哲学层面看，Goal 表达一个预期的开发结果，并拥有足够持久的身份和边界，使它能够跨越时间保持意义。其具体实现形式可以继续演化，但下面这条原则应该保持稳定：

> 替换智能体、提供商、机器、会话或提供商内部任务图，不得悄然创建一个不同的开发目标、抹掉原有历史或扩大原有权限。

一个 Goal 最终可能由单个编码智能体执行，也可能由提供商内部的多智能体工作流、确定性自动化、CI/CD 基础设施，甚至人工动作执行。执行拓扑不会自动被提升为权威开发图的一部分。

## Goal 图和 Agent 图属于不同层

概念上可以理解为：

```text
权威开发层

Goal A -----> Goal B -----> Goal D
                 \
                  -----> Goal C

---------------- 执行边界 ----------------

某个已选择的 Goal 可以由以下方式执行：

- 一个智能体；
- 提供商内部任务 DAG；
- 多个子智能体；
- 确定性工具；
- 人工决策或人工动作。
```

## 这不是领域对象模型承诺

本门户有意不定义永久的 `Goal -> Task -> WorkOrder -> Receipt` 层级。具体合同、基数关系、状态词汇和线格式属于对应产品仓库，并且会随着 CLH、CLE、CLF、CLT 的成熟继续变化。

门户真正承诺的是更窄、也更持久的原则：**Goal 不是 Agent，提供商内部执行结构也不会仅因存在就成为权威状态。**
